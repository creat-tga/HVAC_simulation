# 性能优化记录

> 本文档记录 HVAC_simulation 平台前后端各次性能优化的关键点、方法、量化结果与可继续挖掘的方向，方便后续维护参考。

---

## 1. 系统方案详情页（System Scheme Detail View）

### 1.1 背景

`SystemSchemeDetailView` 是平台核心编辑页之一，包含：

- 顶部 hero 指标卡 / 操作按钮
- 三步骤向导：**设备选型 / 控制策略 / 系统图**
- 设备选型 step 下挂多个 `SubsystemEditor`（最多 5 个），每个子系统又包含 `DesignParamsForm` + `ComboEditor`（最多 10 个组合）+ `TowerGroupEditor`
- 单个 `ComboEditor` 内含 ~13 个 `el-input-number`、3 个 `EquipmentPicker`、若干 `el-descriptions`
- 极端情况下单页可达 130+ 个 Element Plus 表单组件

### 1.2 已落地优化

#### A. 接口层 — `/bundle` 聚合端点

- **问题**：详情页加载需依次调用 4–6 个接口（项目 / 方案 / 校验 / 派生 / 控制策略 / 楼栋）。
- **方案**：后端新增 `GET /system-schemes/{id}/bundle`，一次返回全部数据；SQLAlchemy 用 `selectinload` 预加载子系统、组合、塔组等关联，避免 N+1。
- **效果**：6 次串行请求 → 1 次（~18–20 ms 总时延）。

#### B. SQLite 写入提速

- 启用 `journal_mode=WAL`、`synchronous=NORMAL`、`temp_store=MEMORY`、`cache_size=-64000`，并对热点表加索引。
- 解决 `air_cooled` 子系统保存时的 500 错误（关联懒加载在 async 上下文报 `MissingGreenlet` → 显式初始化空集合）。

#### C. 向导步骤切换的"挂载缓存"

- **问题**：在三步骤之间切换时，每次都会 `unmount → mount` 当前 step 内部的整棵子树，造成 1–2 s 卡顿。
- **方案**：维护 `visitedSteps: Set<StrategyStep>`，首次进入时用 `v-if` 挂载，之后改用 `v-show` 切换（即"首次挂载、后续仅显隐"）。

#### D. 子系统级"折叠/展开"

- **问题**：5 个子系统全部默认展开 → 首屏需挂载 5 × ComboEditor，主线程冻结 5–7 s。
- **方案**：
  1. **默认全部折叠**：`expandedSubs: Set<string>` 初始为空，首屏只渲染 5 个轻量级 head bar，首次可见时间从 ~5000 ms 降至 ~290 ms。
  2. **新增子系统自动展开**：保留编辑流畅度。
  3. **持久挂载集合 `mountedSubs`**：子系统首次展开后，无论用户再如何折叠/展开，子树保留在 DOM 中，仅切换 `v-show`。第二次展开耗时由 ~3.8 s → **~435 ms**。

#### E. SubsystemEditor 内部"分层延迟挂载"

- **方案**：`SubsystemEditor` mount 后用 2 帧 `requestAnimationFrame` 延迟挂载 `ComboEditor` / `TowerGroupEditor`，让 `DesignParamsForm` 先出现。
- **效果**：DesignParamsForm 可见时间 2812 ms → **1403 ms**。

#### F. ComboEditor 内部"渐进式渲染"

- **方案**：`visibleCount` 从 1 起步，之后用 `setTimeout(32)` 节奏每 tick 增量贴 1 个 combo block，避免一次性挂载 130+ 个 input 造成主线程冻结。新增 combo 时通过 `watch(combos.length)` 立即放行。
- **效果**：10 个组合全部渲染完毕 4142 ms → **2793 ms**。

#### G. 折叠态轻量信息

- 折叠态仅展示 `· 制冷量 X kW · 制热量 Y kW`（取自 `derived.cooling_capacity_total` / `heating_capacity_total`），值为 0/缺失整段隐藏，不再出现 "-" 占位。

#### H. `shallowRef` 包装只读派生数据

- store 中 `derived` / `validation` / `projectValidation` 改为 `shallowRef`。这些字段只用于显示、子组件不会原地变更其内部对象，避免 Vue 对千余字段的嵌套结构创建深度 Proxy，进一步减轻子组件首次挂载时 reactivity 追踪开销。

#### I. EquipmentPicker 延迟加载

- 移除 `watch(equipmentType, ensureLoaded, { immediate: true })`，改为仅在用户首次打开 popup（`@visible-change`）或 `modelValue` 已有但缓存缺失时再触发设备库加载。子系统首次展开时 N 个 picker 不再同时发起请求与 reactive 解析。

#### J. 子系统首次挂载骨架屏

- `SubsystemEditor` 未挂载但已展开时显示 `el-skeleton`，给用户即时视觉反馈，避免"按了没反应"。挂载延迟 2 帧以确保骨架先绘制。

#### K. ControlStrategyEditor 折叠+持久挂载

- 原本 `el-collapse :model-value="所有子系统"` 默认全部展开，导致 376 个 input 一次性挂载。
- 改为：`activeStrategySubs` v-model 默认仅展开第 1 个；`strategyMountedSubs` 持久集合记录已挂载子系统；用 `v-if="isStrategySubMounted(sub)"` 包裹 `el-collapse-item` 内的重型内容（schedules / 水温 / 主机台数表格 / 水泵频率 等）。
- **效果**：策略 step 首次可见 1457 ms → **1057 ms**；初始挂载 input 数 376 → **200**（首屏减少 47%）。

### 1.3 量化结果（系统 1：10 组合 / 130 个 input）

| 阶段 | 优化前 | 优化后 |
|---|---|---|
| 首屏（5 子系统全部折叠） | ~5000 ms 卡顿 | **~290 ms** |
| 首次展开 - DesignParamsForm 可见 | ~2812 ms | **1362 ms** |
| 首次展开 - 10 个 combo 渲染完毕 | ~4142 ms | **2717 ms** |
| 二次展开（已挂载） | ~3800 ms | **~409 ms** |
| 三步骤之间切换 | 1–2 s | <100 ms |
| 控制策略 step 首次可见 | ~1457 ms | **~1057 ms** |
| 控制策略首屏 input 数量 | 376 | **200** |

## 2. 关键经验与避坑

1. **Element Plus 单组件挂载成本不可忽略**：`el-input-number`、`el-descriptions`、`el-radio-group` 内部都有较重 setup，130 个 input ≈ 2 s 主线程时间。**优化优先级：减少同时挂载数量 > 减少 reactivity > 减少 props 复杂度**。
2. **"延迟挂载"比"懒加载组件"更通用**：`defineAsyncComponent` 仅在分包场景有意义；同 chunk 内的组件用 `v-if + ref` 配合 `requestAnimationFrame` 即可达到延迟挂载效果。
3. **持久 DOM > 重复挂载**：用户高频切换的视图（向导步骤、子系统折叠），第一次 mount 后切到 `v-show`，避免重复构造组件树。
4. **`requestAnimationFrame` 与 `setTimeout` 的差异**：Vue 在同一 microtask 内会合并多次响应式更新；若想让浏览器在每次更新之间真正完成绘制，需用 `setTimeout` 而非纯 rAF。
5. **`structuredClone` 会破坏 Vue Proxy**：复制 reactive 对象时使用 `JSON.parse(JSON.stringify(...))` 或专用的 `cloneJson` 工具。
6. **SQLAlchemy async 懒加载陷阱**：在 async session 中访问未预加载的关联属性会抛 `MissingGreenlet`。**对策**：`selectinload` 预加载，或在 schema 序列化前显式赋值空集合。

## 3. 待挖掘的优化方向

按"投入产出比 / 改造影响范围"由高到低：

### 3.1 首次展开仍偏慢（DP 可见 1.4 s）— 中性价比

- **`derived` prop 用 `markRaw`**：派生数据是只读的，没必要被 Vue 深度响应式追踪，可以减少 `el-descriptions` 内部 reactive trace 开销。
- **冻结 `subsystem_level_issues` 等只读列表**：`Object.freeze` 或 `shallowRef` 包装传入的 `issues` 数组。

### 3.2 EquipmentPicker 优化 — 中

- 首次挂载时统一 `ensureLoaded()` 拉取整个设备库；可以改为 **延迟到 popup 打开时再加载**，或使用 `IntersectionObserver` 仅当 picker 滚入视口才加载。

### 3.3 用 `<Suspense>` + 骨架屏 — 中

- `SubsystemEditor` 包一层 `<Suspense>`，顶端先显示骨架（设计参数 4 行 + 组合卡片 outline），实际组件挂载后替换。提升"感知性能"，但对真实指标无影响。

### 3.4 替换 `el-input-number` — 高收益但高风险

- 自研轻量 `<NumberInput>`：原生 `<input type="number">` + 简易加减按钮。可移除 ~70% 单组件挂载成本，但需要重新实现 `value-on-clear`、`step`、`precision` 等行为，且涉及全站统一替换。

### 3.5 Combo 列表虚拟滚动 — 高

- 用 `vue-virtual-scroller` 让 ComboEditor 仅渲染视口内的 1–2 个 combo，其余按需替换。但 combo 高度差异较大（取决于是否选了型号、四管制 vs 两管制），需要可变高度虚拟列表。

### 3.6 后端校验缓存 — 低

- `/validate-payload` 在用户输入间频繁触发；可以对相同 payload 哈希做 LRU 缓存。

### 3.7 控制策略编辑器 (ControlStrategyEditor) 性能审计 — 待评估

- 当前未深度优化，估计 5+ 个 sub-section + 多个表格也存在挂载瓶颈，可比照子系统编辑器的方案。

### 3.8 路由级代码分包 — 低

- Vite 默认按路由分 chunk，但 SystemSchemeDetailView 自身已经较大；可考虑把 ControlStrategyEditor、SystemDiagram step 拆为异步路由组件。

## 4. 通用 UI 微优化（本轮已修复）

- **滚动条引起的页面跳动**：用 `scrollbar-gutter: stable` 或全局 `html { overflow-y: scroll }` 预留滚动条空间，避免内容展开时页面横向位移。
